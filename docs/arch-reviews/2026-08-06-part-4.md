## Finding 1 — the failure-reporting contract is incoherent

`ContextFileResult` carries a dedicated `warnings: tuple[str, ...]` channel
(`context_files.py:27`), but `resolve_context_files` populates it for exactly **one** of the
four ways context resolution can fail — and that one is the rarest.

| Failure | Where | `result.warnings` |
|---|---|---|
| Declared path does not exist (typo) | `_expand_path:146-148` | **empty** — `_logger.warning` only |
| Glob matches nothing | `_expand_path:140-141` | **empty** — `_logger.warning` only |
| Directory exists but is empty | `resolve_context_files:42-43` | **empty** — `_logger.debug` only |
| File exists but is unreadable / not UTF-8 | `resolve_context_files:48-50` | populated |

Verified by execution:

```
resolve_context_files(['typo.md'], 'ag', d)  -> files=0  warnings=()
resolve_context_files(['*.rst'],  'ag', d)  -> files=0  warnings=()
```

The two cases a human actually hits — a mistyped path and a glob that stopped matching
after a directory moved — produce **no structured signal at all**. And no caller reads
`.warnings` anyway: the only consumers are `prompt_builder.py:43`, which uses
`context_result.files` and ignores the rest, and `brainstorm.py:29`.

The concrete consequence is not cosmetic. `agentharness/data/agents/brainstorm.md:13`
declares its context file as a home-relative plugin-cache glob:

```yaml
context_files:
  - ~/.claude/plugins/cache/superpowers-marketplace/superpowers/*/skills/brainstorming/SKILL.md
```

and its system prompt (`brainstorm.md:19`) then says *"Follow the
**superpowers:brainstorming** skill injected above as your context file"*. If that plugin is
not installed, or the cache layout changes, the glob matches nothing, `warnings` stays
empty, and the agent runs with a prompt that references a skill that was never injected —
silently. The same shape applies to `planner.md` and `developer.md`, which also declare
`context_files`. An agent producing work against absent normative context is exactly the
failure this module exists to prevent.

Note also that the debug line at `context_files.py:43` reports *"Context directory is
empty"* for a missing **file**, so even the log trail misdescribes the case.

Direction: make the structured channel report every non-recoverable resolution failure, or
drop it and give the caller a single explicit signal it is expected to act on. The current
middle state — a channel that exists, is mostly empty, and is read by nobody — gives the
appearance of failure handling without the substance.

## Finding 2 — the module's two public functions do not compose

```
resolve_context_files(declared_paths, agent_name, config_dir) -> ContextFileResult
format_context_section(files: tuple[ResolvedContextFile, ...])  -> str
```

The output of the module's producer is not the input of the module's formatter. Every
caller must know to reach inside and unwrap `.files`. Two properties turn that into a trap
rather than an inconvenience:

- `ContextFileResult` is a frozen dataclass, so it is **always truthy** — including when it
  holds zero files (verified: `bool(resolve_context_files([], ...)) is True`). A
  `if resolved:` guard therefore does not mean "we got files".
- It is **not iterable**, so passing it to `format_context_section` raises
  `TypeError: 'ContextFileResult' object is not iterable` — verified by execution.

The sole production call site walks straight into both (`brainstorm.py:29-31`):

```python
resolved = resolve_context_files(agent_def.context_files, project_root)
if resolved:
    system_prompt = format_context_section(resolved) + "\n\n" + system_prompt
```

— two positional arguments where three are required, and the result object passed where a
tuple is expected. The chain `cli.py:124 → start_brainstorm → run_brainstorm_session` is
unguarded, and the shipped `brainstorm.md` declares `context_files`, so
`agentharness brainstorm` raises before `os.execvp` is reached. `prompt_builder.py:43` gets
it right, but it is itself only reached from tests today — so the module currently has no
correct production caller at all.

I am reporting this against **this** part, not against `brainstorm.py`, because the
correction belongs in this module's API shape: a producer whose result cannot be handed to
its own formatter, and whose emptiness cannot be tested by truthiness, will keep producing
this class of caller bug. The broken line in #6 is evidence, not the finding.

Direction: make the two functions compose — have `format_context_section` accept the result
type the module produces (or have the producer return the tuple the formatter takes), and
give `ContextFileResult` an emptiness semantics that a caller's `if` will read correctly.

## Considered and not filed

- **`display_path` asymmetry.** A file declared directly keeps its declared path
  (`_expand_path:157`), while the same file reached through a directory or glob gets an
  absolute `str(f)` (`:124`, `:142`, `:155`), so machine-local paths land in the prompt.
  This is deliberate and pinned by tests (`test_context_files.py:92-104`); the consequence
  is prompt-text noise, not a defect I can state a concrete failure for.
- **No cap behind `_SIZE_WARNING_BYTES`.** Warn-only is exactly what `CLAUDE.md`
  documents. Following the documented decision is not a finding.
- **`/**` beats glob in the precedence at `_expand_path:111-126`,** so `a/*/b/**` resolves
  to a literal path and logs a misleading "not found" (verified). Real, but no declared
  `context_files` entry in the repo uses that shape; too marginal to file.
- **Doc drift in `CLAUDE.md`'s signature for this module.** Belongs to part #14 per the
  map's own instruction.
- **Missing tests.** Coverage here is 306 test LOC against 176 source LOC and is genuinely
  thorough; both findings above are contract problems the tests encode rather than catch.
